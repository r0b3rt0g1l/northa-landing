Building a website is the easy part. The hard part starts the next day: keeping it current, secure and running while someone else publishes content. Now multiply that by fourteen.

Today we run **fourteen municipal transparency portals in Sonora, Mexico**, each with its own `.com.mx` domain, its own certificate and its own team publishing news and documents. This is what we learned going from *building* sites to *running* them every day.

## One platform, fourteen sites

Instead of fourteen different systems, there is a single platform:

- **One template.** Every new portal is born from the same template, parameterized with its municipality's data.
- **One shared backend.** An API (Node.js, Express and Prisma on PostgreSQL) that serves all fourteen.
- **One admin panel.** Each municipality logs into the same admin panel and only sees its own data.

The upside is huge: a security or speed improvement is made once and reaches everyone. So is the risk: a shared mistake also reaches everyone. That's why the next part matters so much.

## Everyone sees only their own data

In a multi-tenant platform, the worst possible failure is one client's account reaching another client's data. We guard against it in three layers:

1. **Context comes from the signed token**, never from what the form sends. Even if someone tampers with a request, the server knows which tenant the session belongs to.
2. **Every write operation is validated** against that context before touching the database.
3. **Files live in per-tenant folders.** One municipality's image can't end up in another's gallery.

And we don't settle for "it should work": isolation between municipalities is **verified by an automated test suite**.

## Onboarding a new client

Adding a municipality shouldn't depend on anyone's memory. We have an onboarding tool that takes it end to end: data, domain, portal and panel.

A small lesson that saved us big problems: new portals are **cloned from the template**, not copied from an existing portal's folder. Copying by hand drags along old settings and credentials that later point where they shouldn't.

## Four rules we learned the hard way

- **Nothing is made up.** Every fact carries a verifiable source or the field stays empty. A government portal that publishes a false fact does more harm than an incomplete one.
- **We verify what's live.** Not the code, not a green test suite: the exact URL where a citizen would see the problem.
- **A pilot before the fleet.** Whatever will be repeated in fourteen places is done right once, fully verified, and only then replicated.
- **Explicit approval on shared systems.** Anything that touches a database with several clients on it is shown before it runs.
